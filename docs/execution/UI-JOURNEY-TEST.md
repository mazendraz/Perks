### ملاحظات Chrome التي لا تُحسب خللًا بالموقع

- قبل الدخول ظهر 401 لفحص `/session` دون جلسة. الرد المحمي متوقع ولا يمنح بيانات أو صلاحيات؛ صفحة الدخول نفسها تعمل. لا تغيير لحماية الجلسة من أجل إخفاء هذا الرد. أي 401 غير متوقع بعد الدخول سيُسجل كفشل مستقل.
- تحذيرات خط Adobe مصدرها chrome-extension، وليست ملفات Nuqta. لم تُعطل الإضافة أو تُغير إعداداتها.
- Firefox أوقفت أداة التحكم استخدامه لعدم دعم سياسة الروابط على Windows؛ ده توقف أداة، وليس خطأ بالموقع. المستخدم طلب الاستكمال على Chrome واتصاله نجح. فحص Network وConsole سيتم من DevTools عبر واجهة Chrome.

## J06 — اتصال تحديث قديم بعد استعادة جلسة العميل

اكتشفت الفحوص الآلية المنفصلة هذه المشكلة أثناء اختبار J05؛ لم يتم اختلاق خطوات أو صور لها داخل الرحلة اليدوية. جولة WebKit سجلت خطأ اتصال SSE متعلقًا بالوصول، وجولة أخرى أخرت ظهور الختم فوق حد الثانية الموجود بالاختبار. [تقرير الفشل المحفوظ](evidence/journey/06-webkit-stamp-delay-before.json).

بعد أن تستعيد REST جلسة الجهاز وتغير cookies وCSRF، كان اتصال SSE القائم يحتفظ بهوية الجلسة القديمة حتى الإشعار التالي أو heartbeat، ولا يستمع لإشارة استعادة الجلسة. أضيف استبدال فوري للاتصال عند الإشارة الموثقة الموجودة، وتجاهل أخطاء الاتصال القديم المتأخرة، وإغلاق الاتصال الفاشل بدل reconnect داخلي غير مضبوط. تظل إعادة المحاولة bounded كل 3 ثوانٍ. لا تغيير للسيرفر أو auth أو RLS أو Origin أو CSRF.

الخطورة متوسطة: تأخر أو فقدان التحديث الفوري بعد تعافي جلسة. أضيف اختبار حتمي باثنين من المستهلكين يثبت تبديل الاتصال فورًا، وتحديثهما مرة واحدة، وعدم تأثير أحداث الاتصال القديم، والتنظيف بعد إغلاق الشاشة. اختبار WebKit القائم يظل يفحص حد الثانية وغياب page errors بلا استثناءات أو تخفيف. الحالة: نجح 32 unit مع اختبار Linux متخطى على Windows، وكل 33 mobile على Chromium وWebKit بلا تخفيف حد الثانية. الإصلاح محفوظ في 2ca05a8؛ التحقق اليدوي للتحديث الحي ضمن باقي الجولة.

الاختبارات الآلية المنفصلة تستخدم fixtures خاصة بها ولا تُحسب دليلًا على إتمام الرحلة اليدوية. بطء اختيار الملف في أداة البراوزر لم يُنسب للتطبيق؛ بعد الاختيار ظهر مؤشر حفظ وانتهى واللوجو ظاهر بالمعاينة بلا console errors.

الـconsole كان بلا أخطاء أو تحذيرات في هذه الشاشة. واجهة البراوزر المتاحة تعرض console logs، ولا تعرض قارئ network مستقلاً؛ لا يُحسب ذلك فحصًا كاملاً لكل طلب شبكة. ستُسجل أي طلبات فاشلة تظهر في console أو الواجهة، مع توضيح محدودية الإثبات.

## J11 — الكاشير مش قادر يرجع لصرف مفتوح بعد ما الشاشة تتقفل

- الخطوة 6، الكاشير. بدأ صرف المكافأة، وبعدين الصفحة اتفتحت من جديد (تاب جديد أو المتصفح اتقفل). محاولة الصرف تاني رجّعت 409، وظهر للكاشير نص داخلي: `CHALLENGE ACTIVE · <uuid>`. العميل كان ممكن يكون أكد بالفعل، والمكافأة بتفضل واقفة لحد ما الطلب يخلص (3 دقايق).
- المتوقع: نفس الكاشير بنفس الجلسة يرجع لنفس الصرف بعد ما يمسح كود العميل تاني. أي كاشير أو جلسة أو فرع تاني يفضل مرفوض. الخطورة: متوسطة، لأنها بتوقف الطابور.
- الإصلاح في `rewards.ts`: لو فيه challenge مفتوح لنفس `cashier_user_id` و`cashier_session_id` والفرع، بيرجع نفس الـchallenge بنفس كود المطابقة، ويتسجل `redemption.resume` في الـaudit. إثبات كود العميل الجديد لسه إجباري قبل الاستئناف، ومفيش تغيير في الصلاحيات أو RLS.
- اختبار: `tests/integration/redemption-resume.test.ts`: نفس الجلسة → نفس الـchallenge والكود. جلسة تانية لنفس الكاشير → `CHALLENGE_ACTIVE` 409. وفيه audit واحد.
- التحقق من الشاشة: تاب جديد للكاشير → امسح كارت → استبدال → ظهر نفس رقم المطابقة → العميل أكد → «المكافأة اتصرفت، بدأ كارت رقم 2».

## J12 — طلب تأكيد الصرف مستخبي ورا كود العميل

- الخطوة 6، العميل. الكاشير بدأ الصرف وكود العميل كان مفتوح (شاشة بيضا كاملة)، أو العميل فتح الكود والطلب لسه معلق. زرار «أيوه، أنا اللي بستبدل» كان تحت الكود ومش باين، والعميل لازم يقفل الكود بنفسه علشان يشوفه.
- الإصلاح: الكود الشخصي مش بيترسم طول ما فيه طلب استبدال مستني العميل، والطلب بيظهر قدامه أوتوماتيك (`scrollIntoView`). الخطورة: متوسطة.
- التحقق من الشاشة: الكود مفتوح → الكاشير بدأ الاستبدال → ظهر طلب التأكيد وأكده العميل → اتصرفت.
